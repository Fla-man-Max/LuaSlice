# Mod Debug Editor

Add a dedicated editor to the local Preview 4 migration, on Windows and Android. It is a diagnostic workspace, not a chart, stage, or save editor. The existing editors, mod activation policy, and release builds stay unchanged outside a debug session.

## Approach

Use an editor-owned preview and playtest. A new HaxeUI state owns the session, embedded stage preview, and floating tool windows. Song tests use the existing `PlayState` as a substate and return to the same editor instance. The alternative, a full state switch and a separate reconstruction of the editor on return, simplifies camera reset but makes window state, interrupted transitions, and cleanup harder to preserve. The editor-owned approach was selected.

## Lifetime and persistence

- Enter through the debug menu, with the requested Android warning on every new session. Create the session only after accepting it. The session has one owner and idempotent cleanup, including partially constructed previews, load failures, and interrupted transitions. Pending callbacks carry a session/preview generation and cannot reattach after disposal.
- Keep preferences and supported script saves in a separate in-memory overlay. Resolve allowlisted vanilla, LuaSlice, and registered mod options through their existing accessors; read through to saved defaults, including when a group override is disabled. Avoid the normal mod option getter's lazy insertion into save data and never hand a mutable saved option object to a preview. Leave installed and enabled mods untouched. Reset clears the overlay and restores transient engine state. Exit detaches hooks, restores original update/draw limits and related settings, removes preview filters/listeners, and discards temporary data. No temporary values are serialized.
- Apply 30–500 integer FPS through runtime update/draw settings, not the normal preference setter (which writes to disk on desktop and is display-driven on mobile). Show measured FPS separately and warn about mobile display and thermal limits.
- Add an explicit diagnostic playtest flag. The current `isChartingMode` check is tied to `ChartEditorState`, and ordinary registered songs can save scores. Gate scores, ranks, progression, achievements, analytics/ads tied to completion, and results routing at their actual call sites. Route finish, loss/abort, and recoverable startup failure back to the owning editor. Keep practice and restart behavior within the preview. Redirect supported script save callbacks to the session store. Arbitrary file writes by already trusted scripts are not reversible or part of that promise.

## Preview and tools

- Use the chart editor's light styling and HaxeUI floating/collapsible window pattern, with separate layouts for Session, Test, Inspect, Overwrite Options, Non-Save, and View. Never attach chart-editing commands or write stage/song assets. Keep UI clicks and touches out of the preview while panels own focus.
- Use registered stage IDs, character data, song variations, and difficulties. Build preview-owned stage and character instances through the existing construction paths; never destroy or mutate cached registry entries as preview instances. Run the stage's existing create, update, and destroy lifecycle, subject to the session's script policy. A stage-only preview does not pretend to provide a chart, song position, or a fake PlayState; callbacks that require those run in song tests. Support character selection, pause/reset, camera/layer inspection, and errors for failed assets. Use real charts as read-only inputs to song tests; HUD changes are session-only and apply through supported layout settings. Apply runtime-safe visual options immediately; label any setting that needs a preview restart.
- Use typed, live object handles and an allowlist of editable visual properties. Snapshot first edits, reset safely, and invalidate handles on replacement/destruction. Apply the same ownership rules to supported shader uniforms and filters; unsupported controls must be labeled, not simulated.
- Connect script status, errors, callbacks, and per-instance enablement at the current LuaSlice Lua, Psych Lua, HScript/Polymod, SScript and NxScript loader/dispatch boundaries. Force selection lasts until reset or session exit. After the request's “Experimental Script Execution” confirmation, allow selecting a normally skipped but compatible script from an authorized active source where its actual loader can construct and bind it to this preview. Bypass only explicit advisory checks with a verified backend path; if a backend offers no safe path, explain the restriction in its inspector. Never bypass parsing, incompatible runtime/ABI requirements, permissions, fatal errors, or a disabled mod's activation boundary. Disable only supported nonfatal popup presentation; keep logs and a visible error count.
- Use bounded records for events and recent errors. Reuse the script profiler for opt-in CPU timings and report frame time, FPS, process memory where available, and missing assets. Export only on request and redact sensitive paths. Pause/filter/clear diagnostics without affecting the preview.

## Touch and verification

Reuse the native HaxeUI input integration, touch pointer, and platform back controls. On Android, provide larger touch targets and on-screen pause/return actions. Back closes a focused dialog first, pauses/returns from a test second, and requests session exit otherwise. Restore focus/cameras after returning from a test or resuming the app; activity recreation starts a clean session.

Build in stages: session and no-save regression tests first, then native UI/stage/song lifecycles, then diagnostics and Android interaction. Run Windows native tests against the current Preview 4 build; exercise stock and fixture mod stages/songs, all three FPS cases, error logging without popups, invalid assets and scripts, repeated entry/exit, and byte-for-byte normal save comparison before/after diagnostic tests. Verify Android compilation and device/emulator behavior separately; do not infer touch support or startup from a desktop test. Keep implementation details such as bounded-buffer sizes, window placement defaults, and exact allowlisted properties flexible where the current APIs dictate them. Report gaps explicitly.
